## С1. Первичное наполнение: импорт ВМ и сетевых взаимодействий

**Цель:** перенести существующие таблицы учёта в CMDB кусками, по одной ИС за раз.
**Предусловия:** admin создал ИС и внёс УЗ в их перечни (С12); пользователь — editor и в перечне ИС;
серверы, гипервизоры, сети и прочие CI создаются в UI/API, импорта для них в MVP нет.

1. Пользователь открывает «Импорт ВМ», выбирает ИС (параметр), скачивает шаблон файла (FR-15).
2. Заполняет столбцы: DNS-имя и IP (обязательны), `cpu`, `ram_gb`, `disk_gb`, `os`, `environment`, ключ ITSM.
3. Загружает файл; режим «создать или обновить», **dry-run** включён по умолчанию.
4. Отчёт: создано / обновлено / без изменений / пропущено; по каждой пропущенной строке — номер, столбец,
   причина (ошибка или предупреждение); отдельно участники ИС, которых нет в файле (FR-13).
5. Исправляет файл, загружает повторно, нажимает «Применить». Строки применяются по одной
   (подтранзакция на строку, запись в аудит, общий `import_id`); каждая новая ВМ получает `member_of` на ИС из параметра.
6. Затем «Импорт сетевых взаимодействий» для той же ИС: `source`, `target`, `protocol`, `port`, `description`
   (все обязательны, источник и цель — DNS-имена). Источник обязан входить в ИС; цель — любая существующая ВМ.
7. Порядок: сначала ВМ, потом взаимодействия. Взаимодействия между двумя ИС загружаются после загрузки обеих.

**Ошибки и альтернативы (строка пропускается, остальные применяются)**
- Нет DNS-имени или IP, неверный формат IP/имени/порта/протокола, пустое описание → ошибка строки.
- Повтор в файле (то же имя или тот же `protocol`+`port` в паре) → применяется первая строка, остальные отмечены.
- ВМ уже входит в другую ИС → конфликт, строка не применяется.
- IP уже у другой ВМ → предупреждение с именем той ВМ, строка не применяется.
- Ключ ITSM занят → ошибка с указанием занявшего CI.
- Источник не входит в ИС файла, цель не найдена → ошибка строки.
- Нет прав на ИС → отказ на весь файл до разбора строк.
- Отката импорта нет; защита — обязательный dry-run и повторная загрузка исправленного файла.

**Результат:** ВМ и сетевые правила загружены, граф и перечни доступны.

## С2. Ввод в эксплуатацию нового сервера с ВМ

**Цель:** зарегистрировать новое оборудование и то, что на нём развёрнуто.

1. Editor из перечня служебной ИС (например, «Виртуализация») создаёт CI `server` `srv-rack2-08`
   (ИС выбирается при создании; атрибуты — по форме из схемы типа), статус `planned` (FR-1).
2. После монтажа меняет статус на `active`.
3. Создаёт `hypervisor` `esx-04` в той же служебной ИС, добавляет связь `runs_on` → `srv-rack2-08`
   (цель — любой существующий CI допустимого типа, FR-8).
4. Из карточки гипервизора создаёт ВМ кнопкой «+ ВМ на этом хосте»: ИС новой ВМ выбирается из тех, где
   пользователь в перечне; связь `runs_on` → `esx-04` проставляется сразу (FR-31). Добавляет `connected_to` → сеть.
5. Проверяет граф окружения `srv-rack2-08` (FR-9).

**Ошибки и альтернативы**
- Имя занято в рамках типа → ошибка у поля `name`.
- Обязательный атрибут не заполнен / неверный формат → ошибка у конкретного поля.
- Связь уже существует → 409, «связь уже есть».
- CI без ИС создать нельзя; нет прав на выбранную ИС → отказ.
- CI создан не в той ИС → удалить и создать заново (переноса нет; имя можно использовать повторно).

## С3. Анализ влияния перед плановыми работами

**Цель:** перед перезагрузкой `esx-03` узнать, какие ВМ, БД, приложения и ИС пострадают, и кого предупредить.

1. Пользователь находит `esx-03` поиском (FR-2), открывает карточку.
2. Нажимает «Анализ влияния» (FR-10): система идёт **против** стрелок по связям с
   `propagates_impact=true` (включая сетевые взаимодействия) и возвращает все транзитивно зависимые CI.
3. Видит список, сгруппированный по типам и ИС, с глубиной и путём до каждого
   (`Биллинг ← PostgreSQL billing ← vm-01 ← esx-03`), и тот же результат на графе.
4. Видит колонку «Контакт» (`owner`) и поддержку ИС (`support_group`) — кого предупредить.
5. Экспортирует результат в Excel для заявки на изменение.
6. Editor из перечня ИС `esx-03` переводит его в `maintenance`, после работ — обратно в `active`.

**Ошибки и альтернативы**
- Зависимых нет → явное «Влияние не обнаружено».
- Цикл в графе (A→B→A) → каждый CI показан один раз с минимальной глубиной.
- Выведенные (`decommissioned`) скрыты по умолчанию, флажок «показать выведенные».
- Служебный трафик (например, обновления ОС) может расширять результат; в результате доступны фильтры по глубине, типу связи и ИС.

## С4. Поиск причины сбоя

**Цель:** приложение «Биллинг» недоступно — понять, от чего оно зависит, и найти общий компонент.

1. Пользователь открывает карточку `Биллинг`, граф с направлением «зависимости» (downstream), глубина 4.
2. Видит цепочку БД → ВМ → гипервизор → сервер / СХД / сеть и сетевые взаимодействия к другим ВМ;
   статусы узлов подсвечены цветом (`maintenance` — жёлтый). Все узлы видны (читают все).
3. Кликом раскрывает узлы и переходит в карточки (FR-11).
4. Открывает историю изменений подозрительного CI — что менялось недавно (FR-17).

**Альтернатива:** сбой у нескольких приложений — общие зависимости ищутся вручную через граф.
Инструмент «общие зависимости N выбранных CI» — следующий этап.

## С5. Вывод CI из эксплуатации

**Цель:** списать сервер так, чтобы не потерять информацию и не оставить «висящих» зависимых.

1. Editor из перечня ИС CI меняет статус на `decommissioned`.
2. Система показывает все зависимые CI (upstream) не в статусе `decommissioned` полным списком —
   «от этого сервера зависят 3 активных CI» (FR-30).
3. Пользователь либо отменяет и сначала меняет зависимых, либо подтверждает.
4. Позже (по регламенту) CI удаляется — мягкое удаление, связи помечаются удалёнными (FR-4),
   история сохраняется.

**Ошибки и альтернативы**
- Удаление и вывод CI с зависимыми не блокируются: предупреждение и подтверждение.
- Имя удалённого CI можно использовать повторно; восстановление при конфликте имён — ошибка.
- ИС с живыми CI удалить нельзя; убрать CI из его ИС нельзя (только удалить).

## С6. Актуализация данных повторным импортом

**Цель:** раз в месяц обновить атрибуты ВМ из свежей выгрузки гипервизора.

1. Editor загружает файл ВМ той же ИС в режиме «создать или обновить», dry-run.
2. Отчёт: новые ВМ, изменённые (diff по полям «ram_gb: 8 → 16»), без изменений, пропущенные;
   отдельно участники ИС, отсутствующие в файле (ничего не удаляется).
3. Применяет построчно. В аудите — изменения с `source=import` и `import_id`.

**Правила**
- Пустая ячейка не меняет поле; для очистки пишется `<null>`.
- Строка без изменений получает статус «без изменений» и в аудит не пишется.
- Сопоставление по DNS-имени; ключ ITSM не участвует. Совпадение имени с одной ВМ при чужом ключе ITSM → конфликт.

## С7. Расширение модели: новый тип CI или связи

**Цель:** начать учитывать Kubernetes-кластеры, не дожидаясь разработчиков.

1. Admin открывает «Типы», создаёт тип `k8s_cluster`.
2. В редакторе полей добавляет атрибуты: `version` (строка, обязательное), `nodes` (целое ≥ 1),
   `distribution` (список: vanilla / openshift / rke2) — без ручного JSON (FR-5).
3. Открывает тип связи `runs_on`, добавляет допустимые пары `k8s_cluster → vm` (FR-7).
4. Editor из перечня ИС сразу может создавать CI нового типа.
5. Для нового типа связи admin задаёт и схему атрибутов связи (`attribute_schema`) тем же редактором.

**Ошибки и альтернативы**
- Изменение схемы существующего типа: новое обязательное поле без значения по умолчанию →
  запрет сохранения; сужение типа поля → отчёт о несовместимых записях (FR-6).
- Удаление типа, у которого есть CI → запрет; встроенные типы удалить нельзя.

## С8. Разбор «кто и когда поменял»

**Цель:** у ВМ внезапно изменился атрибут или правило — выяснить, кто, когда и как это сделал.

1. Пользователь (любая роль) открывает карточку CI, вкладка «История» (FR-17).
2. Видит ленту событий: дата, автор, источник (`ui` / `api` / `import` / `template`), `import_id`, diff «было → стало».
3. Для широкой картины — общая лента аудита с фильтром по автору, периоду и сущности; в ней же изменения
   перечня УЗ ИС и версий шаблонов.

## С9. Определение ИС, в которую входит CI (API)

**Цель:** внешняя система (мониторинг, ITSM, скрипт) по ВМ, известной ей по DNS-имени, IP или ключу ITSM,
узнаёт ИС ВМ, её критичность и контакты, а также ИС, к которым она обращается.
**Предусловия:** ВМ входит в ИС (`member_of`); клиент — УЗ с ролью не ниже viewer.

1. Находит CI: `GET /api/v1/cis?name=…` или `?ip=…` или `?itsm_key=…` (или по `id`).
2. Запрашивает ИС: `GET /api/v1/cis/{id}/information-systems`.
3. Получает ответ:

```json
{
  "ci": {"name": "app-02.corp.local", "environment": "prod"},
  "member_of": {"code": "CRM", "name": "CRM", "kind": "business",
                "criticality": "business_critical", "business_owner": "…", "support_group": "…"},
  "consumes": [{"code": "BILL", "name": "Биллинг", "kind": "business",
                "via": [{"target": "db-01", "protocol": "tcp", "port": "5432"}]}]
}
```

`consumes` — ИС, к ВМ которых эта ВМ обращается по `network_flow` (один переход).

**Пакетный запрос:** `POST /api/v1/cis/information-systems:batch` — до 500 позиций (DNS-имя / IP / ключ ITSM);
ответ по каждой: найдено, `not_found` или `ambiguous` (IP у нескольких ВМ); частичный успех нормален.

**Ошибки и альтернативы**
- CI не найден → 404 (в пакете `not_found`); ВМ без ИС в норме не бывает.
- Контур (`environment`) возвращается рядом, чтобы потребитель сам решал, как реагировать на test-ВМ из критичной ИС.

## С10. Перечень сетевых взаимодействий ИС

**Цель:** получить полный список исходящих сетевых взаимодействий заданной ИС — все правила,
исходящие от её ВМ. Нужен для согласования правил межсетевого экрана, аудита связности, оценки влияния.
**Предусловия:** ВМ входят в ИС; правила заведены как `network_flow` с `rules[]`.

1. Клиент задаёт ИС: по `id`, `code` или `name`.
2. Система находит ВМ ИС (`member_of`), берёт связи `network_flow`, где ВМ — **источник** (`source_id`).
3. Результат — плоский список, по строке на правило (`rules[]` разворачивается):
   - ВМ-источник (имя, `environment`), ВМ-цель и ИС цели (с `kind`, критичностью);
   - `protocol`, `port`, `description`, `source` правила;
   - признак `internal`: цель входит в ту же ИС.
4. Фильтры: «только внешние» (`internal=false`), контур, протокол, порт. Экспорт в CSV/XLSX.

**API:** `GET /api/v1/cis/{id}/network-rules?direction=outgoing|incoming` — один запрос с соединением
`member_of` и связей, а не цикл по ВМ. `direction=incoming` — правила, где цель — ВМ ИС
(кто к ней обращается); читать входящие может любой, менять — только владелец источника и admin.

**Ошибки и альтернативы**
- ИС не найдена → 404; нет ВМ или правил → 200 с пустым списком и пояснением.
- Объект, переданный как ИС, не имеет тип `information_system` → 422.
- Удалённые ВМ и связи не участвуют; выведенные из эксплуатации скрыты по умолчанию.
- Подсистем нет (иерархии ИС нет). Большой результат → пагинация.

## С11. Шаблон сетевого взаимодействия: создание и применение

**Цель:** не вносить и не копировать одинаковые правила для десятков ВМ («все ВМ ИС ходят на сервер обновлений»).
**Предусловия:** editor; цель — существующая ВМ.

1. Editor создаёт шаблон: название, **одна цель**, список правил (`protocol`, `port`, `description`) — версия 1.
2. Открывает «Применить»: заполняет список ВМ (кнопка «добавить все ВМ из ИС X» подставляет участников ИС,
   список можно править; до 500 ВМ). Видит предварительный просмотр: «создаётся N правил, уже есть M, нет прав на K».
3. Подтверждает. Для каждой ВМ с правами связь «ВМ → цель» создаётся или дополняется: правила добавляются
   в `rules[]` с `source=template`, `template_id`, `template_version`; существующие пропускаются.
   В аудите — одно событие применения (`source=template`).
4. Шаблон правится → создаётся версия 2; ранее применённые правила остаются на версии 1, пока пользователь
   не выполнит «обновить до версии 2» (с предварительным просмотром, только свои ВМ).
5. «Снять применение» удаляет правила `source=template` выбранной версии; шаблон можно пометить устаревшим.

**Ошибки и альтернативы**
- ВМ без прав попадает в отчёт со статусом «нет прав», остальные применяются.
- Шаблон (версию) нельзя удалить, пока на неё есть ссылки в правилах; сначала — «снять применение».
- Правит и удаляет шаблон создатель или admin; применяют все editor'ы к своим ВМ; видят все.
- В MVP шаблоны только для `network_flow`; автоприменения к новым ВМ нет.

## С12. Управление ИС и перечнем учётных записей

**Цель:** создать ИС и определить, кто может менять её и её CI.

1. Admin создаёт ИС: `code`, `kind` (прикладная / служебная), `criticality`, контакты, `sla`.
2. Вносит в перечень УЗ (`preferred_username`) людей и сервисных клиентов, которым можно менять ИС и её CI.
   Каждое изменение перечня пишется в аудит.
3. Для инфраструктуры заводит служебные ИС (`kind=infrastructure`), для общего компонента — отдельную ИС.

**Ошибки и альтернативы**
- Удаление ИС с живыми CI → запрет.
- Код ИС занят → ошибка у поля `code`.
- Переноса CI между ИС нет; ошибочную принадлежность исправляют удалением и повторным созданием.

## Принятые решения

| #   | Вопрос | Решение |
|-----|--------|---------|
| Р1  | Импорт с ошибками в части строк | Построчно: валидные применяются, ошибочные пропускаются; дубли игнорируются; отката нет |
| Р2  | Создание дочернего CI из карточки | Да, в MVP |
| Р3  | Выведенные CI в анализе влияния | Скрыты по умолчанию, флажок |
| Р4  | Имя удалённого CI | Можно использовать повторно; восстановление при конфликте — ошибка |
| Р5  | «Общие зависимости N CI» | Следующий этап |
| Р6  | Удаление/вывод CI с зависимыми | Предупреждение со списком + подтверждение |
| Р7  | Пустая ячейка при импорте | Не менять; `<null>` — очистить |
| Р8  | CI отсутствует в файле импорта | Не трогать, показать в отчёте (участники ИС) |
| Р9  | Правила внутри самой ИС | Включать с признаком `internal`, фильтр «только внешние» |
| Р10 | Подсистемы ИС | Иерархии ИС нет |
| Р11 | Входящие взаимодействия ИС | Тот же эндпоинт, `direction=incoming`, в MVP |

Другие решения: читают все, пишут по перечню УЗ ИС и роли editor; роль `security_admin` не вводится;
CI входит ровно в одну ИС, создаётся только внутри ИС, переноса нет; ИС с живыми CI не удаляется;
история видна всем; общие компоненты и инфраструктура — в отдельных ИС; шаблоны версионируются.
